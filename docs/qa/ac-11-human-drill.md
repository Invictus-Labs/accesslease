# AC-11 independent operator drill (HUMAN-ONLY)

AC-11: "Release documentation includes installation, upgrade, backup, restore and failure diagnosis; a fresh operator can execute the synthetic smoke procedure."

No agent may mark AC-11 PASS. Its matrix status stays `PENDING_HUMAN_RECEIPT` until a person who did not build AccessLease completes this drill and files the receipt below. An agent-run drill (`node scripts/fresh-operator-smoke.mjs`) is supplemental evidence only and must be labelled `SUPPLEMENTAL, AGENT-RUN` wherever it is cited; it never substitutes for the human receipt.

## Who may run it

A person who has not written, reviewed or tested AccessLease code. They get the repository (or a release archive) and the documentation, nothing else. The facilitator may only observe and write things down. Every question the operator asks, every hint given and every command the facilitator types is an "assistance" and goes into the receipt.

## Preparation (facilitator, before the clock starts)

1. A clean machine or fresh user account with Docker (Compose v2), `openssl`, `curl`, a terminal and a browser. No AccessLease checkout, no `node_modules`, no `.env` files, no containers, networks or volumes whose names start with `accesslease`.
2. Note the machine description: operating system and version, Docker version. Do not record hostnames, IP addresses, usernames or e-mail addresses.
3. Give the operator the repository location and one sentence: "Install this from the documentation and run the synthetic smoke procedure. Tell me when you believe you are done. Think aloud."
4. Start the stopwatch when the operator opens `README.md`. Record the UTC start with `date -u +%Y-%m-%dT%H:%M:%SZ`.

## Steps the operator performs

The source of truth is the documentation itself: `README.md` and `docs/runbook/` (`install.md`, `smoke.md`, `upgrade.md`, `backup-restore.md`, `diagnosis.md`). A step is complete only when its check passes. Record start time, end time, outcome (`pass`, `pass with assistance`, `fail`) and the exact point of confusion for each step.

| # | Step | Document | Check |
| --- | --- | --- | --- |
| 1 | Prepare `.env` from `.env.example` with generated values | `install.md` section 2, `smoke.md` top | `.env` exists with owner-only permissions; no placeholder left; the operator generated the secrets |
| 2 | Part A: the offline proof (`compose.offline.yaml`) | `smoke.md` Part A | the log ends with `OFFLINE SMOKE PASSED` and the compose exit code is 0; the operator can say why exit code 4 from the demo step is expected and is not success |
| 3 | Part B: inspect the demo report, verify the bundle, run the tamper test | `smoke.md` Part B | the report says SYNTHETIC, shows one unresolved lease that is not green, `verify-bundle` exits 0, the tampered and truncated bundles both exit 2 |
| 4 | Install and start the application, create the first administrator (no default password) | `install.md` section 2, `smoke.md` Part C | `/api/v1/health/ready` reports ready; the operator signs in with a password chosen or generated by the tool, nobody dictated one |
| 5 | Part C steps 1 to 4: request, reject bad requests (wildcard, over-long), approve, retrieve the credential once | `smoke.md` Part C | the lease reaches Active; the wildcard and the 600-minute requests are refused; the credential cannot be retrieved twice and is not in the address bar or browser storage |
| 6 | Part C step 5: wait for expiry and watch the state | `smoke.md` Part C | the state reaches `Revoked (verified)` only after verification; the operator can point to the verification reference and explain why "expired" is not "revoked" |
| 7 | Part C steps 6 to 8: explicit revoke, close task, viewer role | `smoke.md` Part C | both end verified with the right reason; the viewer cannot approve or revoke |
| 8 | Part D: report, export, verify, import into a clean installation | `smoke.md` Part D | `report` and `export` write owner-only files; the bundle verifies; importing twice reports "already imported"; the tampered bundle is refused with exit 2 |
| 9 | Take a backup and restore it into a second, clean location | `backup-restore.md` | a backup archive exists and is verified; the restored installation lists the same leases; the operator states why external outcomes must be reconciled before enabling writes after a restore |
| 10 | Walk through the upgrade procedure up to, not including, the upgrade command | `upgrade.md` | the operator names "stop workers, back up, test the restore" in their own words and finds the rollback section |
| 11 | Provoke one documented failure (stop the database) and diagnose it from the documentation only | `diagnosis.md` | the operator runs `doctor`, names the failing component, the exit code, and the documented next action; then finds the pages for `ISSUE_UNKNOWN` and `REVOCATION_UNCONFIRMED` |
| 12 | Clean up everything the drill created | `smoke.md` Cleanup | the facilitator verifies that no container, volume, network or directory with an `accesslease` or `al-` name remains |

Part E of `smoke.md` (the real local provider) is optional for AC-11; note whether it was attempted.

## What the facilitator records (the receipt)

- Operator identity: a name or stable pseudonym, plus one line on relevant experience. Never an e-mail address or username.
- Timing: UTC start and end, total minutes, and minutes per step. The PRD activation target is a synthetic core workflow within 30 minutes of install; record whether it was met.
- Every assistance, verbatim: question, answer, what the operator did next, and whether the documentation should have prevented the question.
- Step outcomes (table above), with the exact documentation line that misled or was missing for every non-clean step.
- Documentation defects found, each with a severity (blocking, confusing, cosmetic).
- Cleanup receipt: the commands run and the output of `docker ps -a`, `docker volume ls` and `docker network ls` filtered for `accesslease` and `al-`, showing nothing left, plus removal of the working directory.
- Any data-safety or security concern the operator raised.

## Pass rule

AC-11 may be recorded as PASS by a human only if: all twelve steps are `pass` or `pass with assistance` where each assistance is logged and judged non-blocking by the facilitator, no step relied on knowledge that is not in the documentation, cleanup left nothing behind, and the receipt is complete. Any `fail`, any missing receipt field or an unlogged assistance makes the drill FAILED; fix the documentation and repeat with a different person.

## Filing

Save the completed receipt as `docs/qa/receipts/ac-11-human-receipt.md` using the template below, then change the AC-11 row of `docs/qa/ac-matrix.md` from `PENDING_HUMAN_RECEIPT` to `PASS` (a human action). The gate refuses a PASS unless the receipt contains the three machine-checked lines `Performed-by: human`, `Identity:` and `Cleanup receipt:`.
